## 2. สรุปวิธีต่างๆ ข้อดี และเหตุผลเชิงเทคนิค (Why & Advantages Matrix)

ตารางนี้สรุปภาพรวมคำตอบสำหรับคำถาม **"แต่ละวิธีมีข้อดีอย่างไร และทำไมถึงเลือกใช้แบบนี้"** ซึ่งเป็นหัวใจสำคัญของวิชา Computer Networks:

```mermaid
flowchart TD
    User["ผู้ใช้ทั่วไป / ผู้โจมตี (Internet)"] --> L3L4["Layer 3 / 4: Network Filtering"]
    subgraph S1["1. Network Layer (L3/L4)"]
        L3L4 --> IPSET{"ipset (th_allow)<br/>1,195 CIDR Blocks"}
        IPSET -- "IP ต่างประเทศ" --> DROP["iptables -j DROP<br/>(สกัดกั้นก่อนถึงเซิร์ฟเวอร์)"]
        IPSET -- "IP ประเทศไทย" --> FW_ACCEPT["ส่งต่อเข้าพอร์ต 80/443"]
    end
    
    subgraph S2["2. Transport / Web Layer (L7 Frontend)"]
        FW_ACCEPT --> NGINX_FE["Nginx Frontend (Reverse Proxy)<br/>• TLS 1.2/1.3 & HSTS (Let's Encrypt DNS-01)<br/>• Nginx Rate Limiting (wp-login.php)<br/>• Edge Rules (บล็อก /xmlrpc.php, ?author=)"]
        NGINX_FE -- "พฤติกรรมผิดปกติ" --> RESP_403["ตอบกลับ HTTP 403 / 429 ทันที<br/>(ไม่เปลืองโหลด PHP/DB)"]
        RESP_403 -. "ล็อกอินผิดพลาดซ้ำๆ" .-> F2B["Fail2ban ตรวจจับ Error Log<br/>--> สั่ง iptables DROP ชั่วคราว"]
    end
    
    subgraph S3["3. Application & Data Layer (L7 Backend)"]
        NGINX_FE -- "คำขอปกติ / Cache Miss" --> NGINX_BE["Nginx Backend (127.0.0.1:8080)<br/>+ FastCGI PHP-FPM 8.3"]
        NGINX_BE --> WP["WordPress CMS"]
        WP --> DB[("MySQL Database<br/>(Localhost Only - ไม่เปิดสู่ภายนอก)")]
    end
```

| วิธีการ / เทคโนโลยีที่ใช้ | ข้อดี (Advantages) | ทำไมถึงเลือกใช้แบบนี้? (Why this approach?) |
| :--- | :--- | :--- |
| **1. ipset ร่วมกับ iptables (GeoIP th_allow)** | • สกัดกั้นบอตต่างประเทศ (>90%) ตั้งแต่ Network Layer ก่อนถึงเว็บเซิร์ฟเวอร์<br>• ประหยัด RAM, CPU และ Bandwidth ของเซิร์ฟเวอร์ | **O(1) vs O(N) Complexity:** การใส่ IP ช่วงไทย 1,195 บล็อกลงใน iptables ตรงๆ จะทำให้เคอร์เนลต้องสแกนทีละบรรทัดแบบ Linear Search (O(N)) จนระบบหน่วง แต่การใช้ `ipset` เป็นโครงสร้าง **Hash Table (O(1))** ทำให้ความเร็วในการตรวจสอบ IP 1,195 ช่วง เร็วเท่ากับการตรวจ IP เพียงตัวเดียว |
| **2. สถาปัตยกรรม Two-Tier Nginx (แยก Frontend ออกจาก Backend)** | • **Security Isolation:** ป้องกันไม่ให้แอปพลิเคชันหลังบ้าน (PHP-FPM, MySQL) สัมผัสกับอินเทอร์เน็ตภายนอกโดยตรง<br>• มี FastCGI Caching ช่วยลดโหลดเซิร์ฟเวอร์ | **Edge Dropping:** Nginx ด้านหน้ารับบทเป็นกันชนคัดกรองคำขอขยะ (เช่น `/xmlrpc.php`, `?author=1`) และตอบกลับ `HTTP 403 Forbidden` ตั้งแต่ชั้นหน้าบ้าน โดยคำขอขยะเหล่านี้ **ไม่เคยวิ่งไปถึง PHP-FPM หรือ MySQL เลย** ทำให้ฐานข้อมูลไม่ล่ม |
| **3. Let's Encrypt ผ่าน DNS-01 Challenge** | • เข้ารหัสการสื่อสารด้วย HTTPS (TLS 1.2/1.3) และเปิดใช้ HSTS<br>• ขอและต่ออายุใบรับรองอัตโนมัติผ่าน DuckDNS | **แก้ข้อจำกัดของ GeoIP Firewall:** เซิร์ฟเวอร์ Let's Encrypt ตั้งอยู่ในต่างประเทศ หากใช้ `HTTP-01 Challenge` ระบบของ Let's Encrypt จะเชื่อมต่อพอร์ต 80 เข้ามาไม่ได้เพราะติดไฟร์วอลล์บล็อกต่างประเทศ การใช้ `DNS-01 Challenge` ตรวจสอบผ่าน DNS TXT Record จึงเป็นวิธีเดียวที่ทำให้ขอ SSL สำเร็จโดยไม่ต้องเปิดพอร์ตให้ทั่วโลก |
| **4. Fail2ban ร่วมกับ Nginx Rate Limiting** | • ป้องกันการโจมตีแบบ Brute Force รหัสผ่าน<br>• ปรับเปลี่ยนสถานะการลงโทษแบบไดนามิก (Stateful Active Defense) | **Stateless vs Stateful:** Nginx Rate Limit ทำได้แค่หน่วงเวลาหรือตอบ 429 แต่ผู้โจมตียังคงส่งแพ็กเก็ตเข้ามาได้เรื่อยๆ การเสริมด้วย Fail2ban จะดักจับผู้ที่ล็อกอินผิดซ้ำๆ แล้วสั่งให้ `iptables` ตัดการเชื่อมต่อที่ระดับเคอร์เนล (DROP) ทำให้บอตหยุดยิงทันที |
| **5. AI SecOps แบบ Read-Only & IP Masking** | • แปลงบันทึก Log หลายหมื่นบรรทัดเป็นบทสรุปเชิงลึกที่เข้าใจง่ายใน 30 วินาที<br>• มีข้อเสนอแนะเชิงป้องกัน (Actionable Recommendations) | **Zero-Trust & Privacy:** มีการ Masking ปิดบังเลขท้าย IP (เช่น `34.182.207.x`) ก่อนส่งไปยังโมเดล LLM เพื่อคุ้มครองความเป็นส่วนตัว และกำหนดให้ AI เป็น **"ที่ปรึกษาแบบอ่านอย่างเดียว"** ห้ามสั่งแก้ไขระบบเครือข่าย เพื่อป้องกันปัญหา AI ทำงานผิดพลาด (Hallucination) |
| **6. SecDash Control API พร้อม Admin Self-Ban Protection** | • ผู้ดูแลระบบสามารถกดปลดแบน (Unban) หรือบล็อก IP เพิ่มเติมได้แบบ Real-time ผ่านเว็บ<br>• มีบันทึกประวัติ (Audit Logs) ถาวร | **Operational Safety:** หากแอดมินเผลอคลิกบล็อก IP ตัวเอง เซิร์ฟเวอร์จะถูกตัดขาดทันที จึงต้องสร้างระบบตรวจสอบ `request.client.host` และ `X-Real-IP` ทั้งในระดับ UI และ API เพื่อปฏิเสธการบล็อก IP ของแอดมิน ป้องกันไม่ให้ระบบล็อกตัวเอง |

### บทที่ 1 บทนำ (หน้า 5–6)
* **หัวข้อ 1.1 ที่มาและความสำคัญ (สิ่งที่ควรเสริม):**
  * ขยายความเรื่องแนวคิด **Defense-in-Depth (การป้องกันแบบหลายชั้นเชิงลึก)** อธิบายว่าเหตุใดการมี Firewall เพียงอย่างเดียว หรือการมีเว็บแอปพลิเคชันเพียงอย่างเดียวจึงไม่เพียงพอในการรับมือภัยคุกคามยุคปัจจุบัน
* **หัวข้อ 1.3 ขอบเขตของโครงงาน (สิ่งที่ควรเสริม):**
  * เพิ่มเติมขอบเขตของ **SecDash Control API** ที่สามารถสั่งการแก้ไขกฎ iptables และ fail2ban ได้จริงแบบ 2-way communication ไม่ใช่เพียงการแสดงผลสถิติแบบ Static

### บทที่ 2 ทฤษฎีและเทคโนโลยีที่เกี่ยวข้อง (หน้า 7–8)
* **หัวข้อ 2.4 Firewall และการกรอง IP (สิ่งที่ควรเสริมในหน้า 7–8):**
  * **ใส่เหตุผลเรื่อง Time Complexity:** อธิบายความแตกต่างระหว่าง Linear Scan ของ iptables ปกติ กับ Hash-based Lookup ของ `ipset` ที่ช่วยให้การเทียบเคียง 1,195 CIDR blocks มีประสิทธิภาพระดับ $O(1)$
  * **ระบุข้อจำกัดของ GeoIP:** ระบุชัดเจนว่า GeoIP เหมาะสำหรับลดพื้นที่การถูกโจมตี (Attack Surface Reduction) แต่ไม่สามารถป้องกันผู้โจมตีที่ใช้ Proxy หรือ VPN ภายในประเทศไทยได้ จึงจำเป็นต้องมีมาตรการชั้นถัดไป (Defense-in-Depth)
* **หัวข้อ 2.5 เว็บเซิร์ฟเวอร์และ Reverse Proxy (สิ่งที่ควรเสริมในหน้า 8):**
  * เพิ่มคำอธิบายเรื่อง **Two-Tier Architecture**: การแยก Nginx Frontend (Edge) ให้ทำหน้าที่ TLS Termination, Rate Limiting และ Caching เพื่อปกป้อง Nginx Backend และ PHP-FPM ไม่ให้ต้องประมวลผลคำขอที่ไร้ประโยชน์

---

### บทที่ 3 วิธีดำเนินงาน (หน้า 9–10)
* **หัวข้อ 3.1 ภาพรวมสถาปัตยกรรม (สิ่งที่ควรเสริมในหน้า 9):**
  * ในตารางสรุปชั้นระบบ ควรระบุ Protocol และ Port ให้ชัดเจนยิ่งขึ้น เช่น:
    * ภายนอก $\rightarrow$ DNS Port 53, HTTPS Port 443
    * เครือข่าย $\rightarrow$ Linux iptables (Layer 3/4)
    * เว็บด้านหน้า $\rightarrow$ Nginx Reverse Proxy (Layer 7)
    * แอปพลิเคชัน $\rightarrow$ Loopback `127.0.0.1:8080` (FastCGI Unix Socket)
    * ฐานข้อมูล $\rightarrow$ MySQL `127.0.0.1:3306`
* **หัวข้อ 3.4 การตั้งค่าความปลอดภัยเครือข่าย (สิ่งที่ควรเสริมในหน้า 10):**
  * **ข้อ 8 (DNS-01 Challenge):** เพิ่มเหตุผลว่าทำไมถึงเลือก DNS-01 แทน HTTP-01 เพราะระบบติดเงื่อนไข GeoIP Firewall
* **หัวข้อ 3.5 การติดตั้ง Dashboard และ AI (สิ่งที่ควรเสริมในหน้า 10):**
  * เพิ่มหัวข้อย่อย **"การควบคุมไฟร์วอลล์แบบ Real-time ผ่าน API และระบบป้องกัน Admin Self-Ban"**:
    * อธิบายว่า SecDash มี Backend API (FastAPI) ที่เชื่อมต่อกับคำสั่ง `iptables` และ `fail2ban-client`
    * มีการสร้างฟังก์ชันดักจับ IP ผู้ดูแลระบบ เพื่อป้องกันไม่ให้ผู้ดูแลระบบเผลอสั่งบล็อกการเชื่อมต่อของเครื่องตนเอง

### บทที่ 4 ผลการดำเนินงานและการทดสอบ (หน้า 11–13)
* **หัวข้อ 4.1 ผลการทำงานของระบบ (การแก้คำบรรยายภาพในหน้า 11–12):**
  * **เปลี่ยนชื่อภาพ 4.1:** *ภาพที่ 4.1 หน้าจอแสดงผลรวมสถิติทราฟฟิก กราฟแนวโน้ม และสถานะการป้องกันของ SecDash*
  * **เปลี่ยนชื่อภาพ 4.2:** *ภาพที่ 4.2 ผลการวิเคราะห์แนวโน้มภัยคุกคามและสรุปสถานการณ์โดย AI (Executive Summary & Key Findings)*

### ตัวอย่างข้อความสำหรับเสริมใน บทที่ 2 (หัวข้อ 2.3 - DNS-01 Challenge)

### ตัวอย่างข้อความสำหรับเสริมใน บทที่ 3 (หัวข้อ 3.5 - SecDash API & Protection)
