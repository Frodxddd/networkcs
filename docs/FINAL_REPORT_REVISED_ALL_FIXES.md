## คำนำ

รายงานฉบับนี้จัดทำขึ้นเพื่ออธิบายการออกแบบ ติดตั้ง และทดสอบระบบเครือข่ายสำหรับให้บริการเว็บไซต์บนเครื่องเสมือนในระบบคลาวด์ โดยใช้ Microsoft Azure เป็นผู้ให้บริการโครงสร้างพื้นฐาน ติดตั้ง Ubuntu Server, Nginx, PHP, MySQL และ WordPress พร้อมเพิ่มมาตรการรักษาความปลอดภัยตั้งแต่การเข้าถึงเครื่อง การกรองทราฟฟิกเครือข่าย ไปจนถึงการตรวจสอบบันทึกการใช้งานและสรุปเหตุการณ์ด้วย AI โครงงานนี้เป็นการประยุกต์แนวคิดแบบจำลอง OSI 7 Layers และ TCP/IP Model ในสถานการณ์จริงบนระบบคลาวด์ โดยเชื่อมโยงการสื่อสารระดับเครือข่ายกับการให้บริการเว็บและการรักษาความปลอดภัยหลายชั้น

เนื้อหาประกอบด้วยพื้นฐานเครือข่ายและเทคโนโลยีที่เกี่ยวข้อง เหตุผลในการเลือกใช้เครื่องมือ ขั้นตอนการดำเนินงาน ผลการทดสอบจากข้อมูลที่บันทึกไว้ ปัญหาที่พบ และข้อเสนอแนะสำหรับการดูแลระบบต่อไป ทั้งนี้ ตัวเลขผลการดำเนินงานอ้างอิงจากเอกสารขั้นตอน บันทึกสถิติ และภาพหน้าจอของระบบ ณ วันที่ 28–29 ตุลาคม 2569

## บทที่ 1 บทนำ

### 1.1 ที่มาและความสำคัญ
เว็บไซต์ที่เปิดให้เข้าถึงผ่านอินเทอร์เน็ตต้องอาศัยทั้งระบบเครือข่าย เว็บเซิร์ฟเวอร์ ฐานข้อมูล และมาตรการรักษาความปลอดภัย หากเปิดบริการโดยไม่จำกัดการเข้าถึง อาจพบคำขออัตโนมัติจากบอต การสแกนหาช่องโหว่ การเดารหัสผ่าน และการเรียกใช้ส่วนประกอบของ WordPress ที่ไม่จำเป็น การป้องกันด้วยไฟร์วอลล์เพียงอย่างเดียวไม่สามารถจัดการคำขอที่ผ่านเข้ามาถึงชั้นเว็บหรือช่องโหว่ระดับแอปพลิเคชันได้ทั้งหมด ขณะเดียวกันการป้องกันเฉพาะในเว็บแอปพลิเคชันก็ไม่สามารถทดแทนการควบคุมการเข้าถึงเครือข่ายได้ จึงควรใช้แนวคิด Defense-in-Depth หรือการป้องกันแบบหลายชั้น เพื่อให้แต่ละชั้นช่วยลดความเสี่ยงและชดเชยข้อจำกัดของชั้นอื่น

โครงงานนี้จึงนำเว็บ WordPress ไปติดตั้งบนเครื่องเสมือน Ubuntu ใน Microsoft Azure และวางมาตรการป้องกันหลายชั้น ได้แก่ การใช้ SSH key แทนรหัสผ่าน การเข้ารหัส HTTPS การจำกัดทราฟฟิกด้วย iptables และ ipset การป้องกันการเรียก XML-RPC การจำกัดอัตราคำขอหน้าเข้าสู่ระบบ การใช้ fail2ban และการวิเคราะห์บันทึกการใช้งานผ่านแดชบอร์ด SecDash โดยแต่ละชั้นมีหน้าที่ต่างกัน ตั้งแต่การกรองการเชื่อมต่อที่ระดับเครือข่าย ไปจนถึงการตรวจสอบคำขอ HTTP และการเฝ้าระวังเหตุการณ์

### 1.2 วัตถุประสงค์
1. เพื่อสร้างเว็บเซิร์ฟเวอร์ที่เข้าถึงได้ผ่านชื่อโดเมนและ HTTPS
2. เพื่อประยุกต์ใช้แนวคิดเครือข่ายและการกรองแพ็กเก็ตในการจำกัดการเข้าถึงบริการ
3. เพื่อเพิ่มความปลอดภัยให้ SSH, WordPress, Nginx และฐานข้อมูล
4. เพื่อรวบรวมและแสดงสถิติจาก HTTP access log และใช้ AI ช่วยสรุปแนวโน้มภัยคุกคาม
5. เพื่อทดสอบการทำงานและบันทึกผลอย่างเป็นระบบ

### 1.3 ขอบเขตของโครงงาน
ระบบประกอบด้วย VM บน Azure, Ubuntu Server 24.04.5 LTS, Nginx 1.24.0, PHP-FPM 8.3, MySQL 8.0, WordPress 6.8, DuckDNS, ใบรับรอง Let's Encrypt, iptables/ipset, fail2ban และ SecDash ที่พัฒนาด้วย Vue 3, TypeScript, Vite และ Tailwind CSS ทั้งนี้ ระบบได้มีมาตรการป้องกัน Admin Self-Ban และบันทึกประวัติการแก้ไขกฎลง Audit Logs เพื่อความปลอดภัยในการบริหารจัดการ

### 1.4 ประโยชน์ที่คาดว่าจะได้รับ
ผู้จัดทำได้ฝึกตั้งค่าเครือข่ายและบริการเว็บบนคลาวด์ เข้าใจการทำงานร่วมกันของ DNS, TCP/IP, firewall, reverse proxy และฐานข้อมูล ตลอดจนเรียนรู้ว่าการอ่าน log และการทดสอบจากหลักฐานมีความสำคัญต่อการประเมินความปลอดภัยอย่างไร

## บทที่ 2 ทฤษฎีและเทคโนโลยีที่เกี่ยวข้อง

### 2.1 พื้นฐานเครือข่ายและการสื่อสาร
การสื่อสารผ่านเครือข่ายอาศัยหมายเลข IP เพื่อระบุปลายทาง และใช้พอร์ตเพื่อแยกบริการบนเครื่องเดียวกัน ตัวอย่างเช่น SSH ใช้พอร์ต 22, HTTP ใช้พอร์ต 80 และ HTTPS ใช้พอร์ต 443 ส่วน subnet mask หรือ CIDR ใช้ระบุส่วนเครือข่ายและส่วนโฮสต์ของ IP การกำหนดกฎ firewall จึงต้องพิจารณาทั้งต้นทาง โปรโตคอล และพอร์ตปลายทาง

เอกสารประกอบการเรียนเครือข่ายที่ค้นพบอธิบายตัวอย่าง IPv4, network address, broadcast address และการแบ่ง subnet เช่น 192.168.1.1/24 ซึ่งมี network address เป็น 192.168.1.0 และ broadcast address เป็น 192.168.1.255 เนื้อหานี้เชื่อมโยงกับโครงงานในส่วนการทำความเข้าใจช่วง IP และการจัดกลุ่มเครือข่ายสำหรับกฎกรองทราฟฟิก

### 2.2 คลาวด์และเครื่องเสมือน
Microsoft Azure ให้บริการเครื่องเสมือน (Virtual Machine: VM) ซึ่งทำหน้าที่เสมือนเซิร์ฟเวอร์ที่เชื่อมต่อเครือข่ายได้ โดยโครงงานใช้ Azure for Students และเลือกภูมิภาค Indonesia Central ตามข้อจำกัดของบัญชีนักศึกษา ขนาดเครื่องที่ระบุคือ Standard_B2als_v2 จำนวน 2 vCPU และ RAM 4 GB

### 2.3 DNS และ HTTPS
DuckDNS ทำหน้าที่เชื่อมชื่อโดเมน nenenainaemak.duckdns.org เข้ากับ Public IP ของ VM ส่วน HTTPS ใช้ TLS เข้ารหัสการรับส่งข้อมูลระหว่างผู้ใช้กับเว็บเซิร์ฟเวอร์ โครงงานใช้ใบรับรอง Let's Encrypt ผ่าน DNS-01 Challenge ซึ่งตรวจสอบสิทธิ์ในโดเมนผ่านระเบียน DNS แทนการให้ผู้ตรวจสอบเชื่อมต่อพอร์ต 80 จากทั่วโลก

### 2.4 Firewall และการกรอง IP
iptables เป็นเครื่องมือกำหนดกฎกรองแพ็กเก็ตใน Linux ส่วน ipset ใช้เก็บชุดเครือข่ายหรือ IP สำหรับนำไปอ้างอิงในกฎ ทำให้จัดการรายการจำนวนมากได้สะดวก โครงงานใช้ชุด th_allow ซึ่งอ้างอิงช่วง IPv4 ของประเทศไทย 1,196 CIDR blocks และตั้งนโยบาย INPUT เป็น DROP หลังอนุญาตทราฟฟิกที่จำเป็น หากใส่รายการจำนวนมากเป็นกฎแยกใน iptables การตรวจสอบอาจต้องไล่พิจารณากฎตามลำดับซึ่งมีลักษณะเชิงเส้น O(N) ขณะที่ ipset ใช้โครงสร้างข้อมูลสำหรับค้นหาสมาชิกแบบแฮชในชุดข้อมูลที่เหมาะสม จึงช่วยลดภาระการตรวจสอบรายการ IP จำนวนมากได้ โดยความซับซ้อนจริงขึ้นกับชนิดชุดข้อมูลและการตั้งค่าที่ใช้

การกรองตามประเทศช่วยลดพื้นที่การถูกโจมตี (Attack Surface Reduction) จากแหล่งที่ไม่จำเป็น แต่ไม่ใช่การยืนยันตัวตนและไม่สามารถรับประกันว่าจะหยุดผู้โจมตีทั้งหมดได้ เพราะฐานข้อมูลช่วง IP อาจเปลี่ยน ผู้ใช้ที่เดินทางหรือใช้ VPN/Proxy ซึ่งมีทางออกในประเทศไทยอาจยังเข้าถึงได้ และผู้ใช้ที่ชอบธรรมอาจถูกปฏิเสธ จึงต้องใช้ร่วมกับมาตรการชั้นอื่นตามแนวคิด Defense-in-Depth

### 2.5 เว็บเซิร์ฟเวอร์และ Reverse Proxy
Nginx รับคำขอ HTTP/HTTPS จากผู้ใช้และส่งต่อไปยังบริการภายในได้ เรียกบทบาทนี้ว่า Reverse Proxy โครงงานแยก Nginx ด้านหน้า (Frontend/Edge) ออกจาก Backend ที่ฟังเฉพาะ 127.0.0.1:8080 เพื่อไม่ให้ Backend เปิดรับการเชื่อมต่อโดยตรงจากเครือข่ายภายนอก สถาปัตยกรรมสองชั้นนี้ช่วยให้ Frontend รับผิดชอบการยุติ TLS (TLS Termination) การจำกัดอัตราคำขอ การปฏิเสธ path ที่ไม่ต้องการ และการทำ Cache สำหรับคำขอที่เหมาะสม จึงช่วยลดคำขอที่ต้องส่งต่อไปยัง Backend, PHP-FPM และฐานข้อมูล ทั้งนี้ Cache ต้องตั้งค่าอย่างระมัดระวังเพื่อไม่ให้ข้อมูลเฉพาะบุคคลหรือข้อมูลที่ต้องอาศัยสถานะผู้ใช้ถูกเก็บหรือส่งซ้ำผิดคน

### 2.6 การตรวจจับการโจมตีและ AI SecOps
Access log เก็บรายละเอียดคำขอ เช่น IP, path, method, เวลา และรหัสสถานะ HTTP สคริปต์ analyze-logs.py อ่าน log แล้วจัดหมวดหมู่พฤติกรรมที่เข้าข่าย เช่น XML-RPC, การเดารหัสผ่าน, การสแกนช่องโหว่ และการสุ่มค้นหาชื่อผู้ใช้ จากนั้น secdash-ai.py นำข้อมูลสรุปไปให้ AI วิเคราะห์และเสนอแนวทางรับมือ โดยปิดบังเลขท้าย IP ก่อนส่งข้อมูล และออกแบบให้ AI ทำหน้าที่เป็นที่ปรึกษาแบบอ่านอย่างเดียว

ผลจากการจัดหมวดหมู่ log เป็นการประมาณจากกฎที่เขียนไว้ ไม่ใช่หลักฐานยืนยันว่าทุกคำขอเป็นการโจมตีจริง หรือยืนยันว่าผู้โจมตีเข้าถึงระบบสำเร็จ

## บทที่ 3 วิธีดำเนินงาน

### 3.1 ภาพรวมสถาปัตยกรรม
เส้นทางหลักของคำขอคือ ผู้ใช้ → DNS ของ DuckDNS (พอร์ต 53) → Public IP ของ Azure VM → กฎเครือข่าย Linux ด้วย iptables/ipset (ชั้น L3/L4) → Nginx Frontend/Reverse Proxy บน HTTPS พอร์ต 443 (ชั้น L7) → Nginx Backend ที่ 127.0.0.1:8080 → PHP-FPM ผ่าน FastCGI → WordPress → MySQL ที่เชื่อมต่อเฉพาะภายในเครื่องบนพอร์ต 3306 ขณะเดียวกัน access log จะถูกประมวลผลเป็นรายงาน JSON และแสดงผลบน SecDash

*(แผนภาพสถาปัตยกรรม ภาพที่ 3.1, 3.2, 3.3)*

### 3.2 การเตรียมเครื่องเซิร์ฟเวอร์
1. สมัคร Azure for Students และสร้าง VM ชื่อ nw-server ในภูมิภาค Indonesia Central ด้วย Ubuntu Server 24.04 LTS
2. ตั้งค่าการเข้าถึงด้วย SSH public key และใช้บัญชี deploy แทนการเข้าเป็น root โดยตรง
3. เชื่อมชื่อโดเมน nenenainaemak.duckdns.org กับ Public IP ของ VM
4. ติดตั้ง Nginx, MySQL, PHP-FPM และส่วนขยาย PHP ที่ WordPress ต้องใช้
5. สร้างฐานข้อมูล wordpress และผู้ใช้ wpuser พร้อมกำหนดสิทธิ์เฉพาะฐานข้อมูลที่จำเป็น
6. ดาวน์โหลด WordPress และตั้งค่า Nginx เบื้องต้นเพื่อให้ทำขั้นตอนติดตั้งผ่านเบราว์เซอร์

### 3.3 การติดตั้งเว็บและ HTTPS
หลังติดตั้ง WordPress แล้ว ได้ขอใบรับรอง Let’s Encrypt ผ่าน DNS-01 Challenge และตั้งค่า Nginx ให้เปลี่ยนเส้นทางจาก HTTP ไป HTTPS พร้อมใช้ TLS 1.2 และ TLS 1.3 และเพิ่ม Strict-Transport-Security (HSTS) เหตุผลที่เลือก DNS-01 คือการยืนยันสิทธิ์ผ่านระเบียน TXT ใน DNS โดยไม่ต้องให้เซิร์ฟเวอร์ตรวจสอบของ Let’s Encrypt เชื่อมต่อเข้าพอร์ต 80 ของ VM โดยตรง ซึ่งเหมาะกับสภาพแวดล้อมที่มีการจำกัดการเชื่อมต่อขาเข้าด้วย GeoIP Firewall ทั้งนี้ ควรตรวจสอบการต่ออายุใบรับรองและสิทธิ์ของ DNS API token อย่างสม่ำเสมอ

### 3.4 การตั้งค่าความปลอดภัยเครือข่าย
1. ตั้งค่า SSH ให้ปิดการล็อกอิน root และการยืนยันตัวตนด้วยรหัสผ่าน อนุญาตเฉพาะ public key และผู้ใช้ deploy
2. ดาวน์โหลดช่วง IP ประเทศไทยมาเก็บใน ipset ชื่อ th_allow และใช้ iptables อนุญาตพอร์ต 22, 80 และ 443 เฉพาะต้นทางที่อยู่ในชุดดังกล่าว โดยต้องตรวจสอบให้แน่ใจว่า Azure Network Security Group (NSG) และกฎภายในเครื่องสอดคล้องกัน และมีช่องทางกู้คืนหากผู้ดูแลถูกบล็อกโดยไม่ตั้งใจ
3. ตั้ง cron ให้อัปเดตรายการ IP ไทยเป็นรายสัปดาห์ โดยตรวจสอบข้อมูลก่อนสลับชุดรายการ
4. กำหนด Nginx ให้ปฏิเสธ /xmlrpc.php และคำขอที่มีพารามิเตอร์ author= รวมถึงจำกัดความถี่การเรียก wp-login.php
5. ติดตั้ง fail2ban สำหรับตรวจจับการล็อกอิน SSH และ WordPress ที่ล้มเหลวซ้ำ แล้วแบน IP ตามช่วงเวลาที่กำหนด
6. แยก Nginx frontend และ backend โดย backend ฟังเฉพาะ 127.0.0.1:8080 และกำหนด cache สำหรับคำขอที่เหมาะสม

### 3.5 การติดตั้ง Dashboard และ AI
สคริปต์ analyze-logs.py ประมวลผล access log และสร้าง report.json ทุกชั่วโมง จากนั้น secdash-ai.py อ่านข้อมูลสรุป ปิดบังเลขท้าย IP ประเมินความผิดปกติ และเรียกใช้ AI เพื่อจัดทำข้อสรุปลง ai_report.json หน้า SecDash สร้างด้วย Vue 3, TypeScript, Vite และ Tailwind CSS และป้องกันด้วย HTTP Basic Authentication ระบบ SecDash Control API (FastAPI) ใช้สำหรับควบคุม iptables และ fail2ban โดยกำหนดการตรวจสอบสิทธิ์ บันทึก Audit Logs และกลไก Admin Self-Ban Protection เพื่อป้องกันผู้ดูแลบล็อก IP ของตนเอง

ก่อนเผยแพร่รายงานหรือภาพหน้าจอ ต้องปิดบังรหัสผ่าน Token API Key และข้อมูลรับรองทั้งหมด โดยระบบจัดเก็บ Log และรายงานสรุปของ AI ได้กำหนดมาตรการพรางหมายเลข IP (Data Anonymization) โดยปิดเลขชุดท้ายเป็น .x เสมอ (เช่น 34.182.207.x หรือ 1.46.128.x) เพื่อรักษาความเป็นส่วนตัวตามหลักความปลอดภัย ทั้งนี้ สำหรับหน้าจอแดชบอร์ด SecDash และบันทึกประวัติ Audit Logs ของผู้ดูแลระบบ (ภาคผนวก ก) ตัวเลข IP ในภาพหน้าจอเป็นหมายเลขที่ใช้ในการจำลองและทดสอบการบริหารจัดการกฎไฟร์วอลล์จริงบนระบบ เพื่อแสดงขั้นตอนการทำงานของส่วนควบคุมไฟร์วอลล์ได้อย่างชัดเจน

## บทที่ 4 ผลการดำเนินงานและการทดสอบ

### 4.1 ผลการทำงานของระบบ
จากเอกสารขั้นตอนและภาพหน้าจอที่แนบ ระบบมีแดชบอร์ดแสดงจำนวนคำขอ HTTP จำนวน IP ที่ไม่ซ้ำ เหตุการณ์ที่จัดเป็นความเสี่ยงสูง กราฟแนวโน้มทราฟฟิก สัดส่วนรหัสสถานะ HTTP รายการเป้าหมายที่ถูกเรียกบ่อย ผลวิเคราะห์จาก AI หน้าจัดการ IP และประวัติการเปลี่ยนแปลง IP

*(ภาพที่ 4.1 หน้าจอแสดงผลรวมสถิติทราฟฟิก กราฟแนวโน้มประจำเดือนตุลาคม 2569 และสถานะการป้องกันของ SecDash)*  
*(ภาพที่ 4.2 ผลการวิเคราะห์แนวโน้มภัยคุกคามและสรุปสถานการณ์โดย AI)*  
*(ภาพที่ 4.3 ข้อเสนอแนะเชิงป้องกัน และสถิติคำขอย้อนหลัง 24 ชั่วโมง)*  

### 4.2 ผลสถิติจาก Access Log
ระบบได้เริ่มเปิดใช้งาน GeoIP Firewall และกฎ Nginx ตั้งแต่วันที่ **10 ตุลาคม 2569 เวลา 22:19 น. (ตรงกับ 15:19 UTC)** เพื่อสกัดกั้นการโจมตีจากต่างประเทศที่พุ่งสูงผิดปกติในช่วงวันที่ 9–10 ตุลาคม 2569 (โดยในวันที่ 24 ตุลาคม 2569 เป็นวันที่เริ่มเปิดใช้งานระบบ Audit Log เพื่อบันทึกประวัติการสั่งบล็อกและปลดแบน IP ด้วยมือผ่านแดชบอร์ด) และได้เก็บรวบรวมข้อมูลสถิติเพื่อเปรียบเทียบผลจนถึงวันที่ 28–29 ตุลาคม 2569 โดยตามข้อมูลสถิติตัดรอบ ณ วันที่ 28 ตุลาคม 2569 มีคำขอ HTTP รวม 29,701 ครั้ง และระบบจัดหมวดหมู่เหตุการณ์ที่เข้าข่ายการโจมตีได้ 13,010 ครั้ง จาก IP ที่ไม่ซ้ำ 660 หมายเลข ตัวเลขนี้เป็นผลจากกฎจำแนกในสคริปต์และควรตีความว่าเป็นเหตุการณ์ที่เข้าเงื่อนไขการตรวจจับ ไม่ใช่จำนวนการบุกรุกที่ยืนยันแล้ว

| ช่วงเวลา | จำนวนคำขอ | เหตุการณ์ที่จัดเป็นการโจมตี | สัดส่วนตามรายงาน |
| :--- | :---: | :---: | :---: |
| ก่อนเปิด Firewall (ก่อน 10 ต.ค.) | 21,916 | 12,964 | 59.2% |
| หลังเปิด Firewall (10–28 ต.ค.) | 7,785 | 46 | 0.6% |

หมายเหตุ: ข้อมูลในตารางที่ 4.2 เป็นสถิติตัดรอบ ณ วันที่ 28 ตุลาคม 2569 (จำนวน 29,701 คำขอ) ส่วนภาพหน้าจอแดชบอร์ดในภาพที่ 4.1 และ 4.2 เป็นการบันทึกข้อมูลสะสมต่อเนื่อง ณ วันที่ 29 ตุลาคม 2569 (จำนวน 30,347 คำขอ ซึ่งมีทราฟฟิกเพิ่มขึ้นตามการใช้งานจริง 646 คำขอ และมีเหตุการณ์โจมตีเพิ่มขึ้น 8 ครั้ง)

เอกสารระบุว่าช่วงก่อนเปิด Firewall มีการเรียก /xmlrpc.php จาก IP ที่ปิดบังเป็น 34.182.207.x จำนวนประมาณ 10,100 ครั้ง และหน้าแดชบอร์ดแสดงเป้าหมาย XML-RPC จำนวนมาก การเปรียบเทียบก่อนและหลังแสดงความสัมพันธ์ระหว่างการเปิดมาตรการกรองกับสัดส่วนเหตุการณ์ที่ถูกจัดประเภท แต่ยังไม่สามารถสรุปว่า firewall เป็นสาเหตุเดียว หรือว่าการโจมตีถูกสกัดกั้นทั้งหมดได้ หากไม่มีการทดสอบควบคุมและหลักฐานเครือข่ายเพิ่มเติม

### 4.4 ข้อจำกัดในการแปลผล
สถิติขึ้นกับกฎจำแนกของ analyze-logs.py เช่น การเรียก xmlrpc.php จะถูกจัดเป็น xmlrpc_abuse ตาม path โดยไม่จำเป็นต้องทราบเจตนาของผู้เรียก และการนับจาก access log จะเห็นเฉพาะคำขอที่มาถึงชั้นเว็บเซิร์ฟเวอร์ ไม่ครอบคลุมแพ็กเก็ตที่ firewall ทิ้งก่อนถึง Nginx ดังนั้นตัวเลขก่อนและหลังจึงอาจใช้ช่วงข้อมูลที่ไม่เท่ากันและไม่ใช่ตัวชี้วัดการบุกรุกโดยตรง

การแปลผลสถิติควรพิจารณาช่วงเวลาที่บันทึกข้อมูลและเวลาที่เปิดใช้มาตรการให้ตรงกัน เนื่องจากจำนวนคำขอในแต่ละหน้าจออาจแตกต่างกันตามเวลาที่เก็บข้อมูล และควรใช้ผลทดสอบจากระบบจริงประกอบการสรุปผล

## บทที่ 5 สรุปผล ปัญหา และข้อเสนอแนะ

### 5.1 สรุปผล
โครงงานนี้ติดตั้งเว็บไซต์ WordPress บน VM ของ Microsoft Azure และเพิ่มมาตรการป้องกันหลายชั้น ตั้งแต่ SSH key, HTTPS, การกรอง IP ด้วย iptables/ipset, กฎความปลอดภัยของ Nginx, rate limiting, fail2ban ไปจนถึงระบบวิเคราะห์ access log และแดชบอร์ด SecDash มีการรวบรวมสถิติจาก log เพื่อใช้ตรวจสอบแนวโน้มทราฟฟิก แนวทาง Defense-in-Depth ช่วยแบ่งหน้าที่การป้องกันตั้งแต่ระดับเครือข่าย จนถึงเว็บแอปพลิเคชัน ทั้งนี้ สถิติจาก log เป็นเหตุการณ์ที่เข้าเงื่อนไขการจำแนก ไม่ใช่หลักฐานยืนยันการบุกรุก หรือยืนยันว่าระบบป้องกันภัยคุกคามได้ทั้งหมด ระบบยังมีฟังก์ชันควบคุมไฟร์วอลล์ผ่าน Web API พร้อมกลไก Admin Self-Ban Protection เพื่อเพิ่มความปลอดภัย

| ขอใบรับรอง DuckDNS ไม่ผ่าน | ตรวจ token ให้ไม่มีอักขระขึ้นบรรทัดใหม่ และเก็บเป็นความลับ |
| AI provider บางรายเชื่อมต่อไม่ได้จากภูมิภาคคลาวด์ | ใช้ระบบ fallback ไปยังผู้ให้บริการสำรองหรือกฎแบบกำหนดแน่นอน |
| ผู้ดูแลอาจบล็อก IP ของตนเองจนขาดการเชื่อมต่อ | เตรียมช่องทางกู้คืนผ่าน Azure Portal Run Command หรือเครือข่ายสำรอง และทดสอบ Admin Self-Ban Protection ทั้งฝั่ง Frontend/API ก่อนใช้งานจริง |

### 5.3 ข้อเสนอแนะ
1. ทบทวนกฎ firewall และรายการ IP ประเทศไทยเป็นระยะ พร้อมมีช่องทางกู้คืนเมื่อผู้ดูแลถูกบล็อกตัวเอง
2. จำกัดพอร์ตที่เปิดใน Azure Network Security Group ให้สอดคล้องกับ firewall ภายในเครื่อง และจำกัด SSH ให้เข้าถึงได้เฉพาะแหล่งที่จำเป็นเมื่อทำได้
3. ตรวจสอบการสำรองข้อมูลเป็นประจำ และทดลองกู้คืนทั้งฐานข้อมูล ไฟล์ WordPress และไฟล์ตั้งค่า
4. ปรับปรุงการจำแนกเหตุการณ์โดยแยกคำขอที่น่าสงสัยออกจากเหตุการณ์ที่ยืนยันแล้ว พร้อมเก็บเวลาของการทดสอบให้ตรงกัน
5. ใช้บัญชีผู้ดูแลเท่าที่จำเป็น อัปเดต WordPress และปลั๊กอิน และพิจารณาถอดปลั๊กอินที่ไม่จำเป็นหรือมีความเสี่ยง
6. เก็บหลักฐานจากคำสั่งจริงและระบุวันที่ทดสอบทุกครั้ง ไม่ควรใช้คำว่า ‘ป้องกันได้ 100%’ หรือ ‘ปลอดภัยทั้งหมด’ จากข้อมูล log เพียงอย่างเดียว

## ภาคผนวก ข หลักฐานผลการทดสอบคำสั่งและการรักษาความปลอดภัย

- **ภาพที่ ข.1:** ผลการทดสอบการเรียกแบบมีพารามิเตอร์ author (`?author=1`) ซึ่ง Nginx ตอบกลับ HTTP 403 Forbidden  
- **ภาพที่ ข.2:** ผลการทดสอบการเรียก `/xmlrpc.php` ซึ่ง Nginx ตอบกลับ HTTP 403 Forbidden และแสดง Security Headers ครบถ้วน  
- **ภาพที่ ข.3:** สถานะการทำงานเริ่มต้นของ Fail2ban สำหรับ jail sshd  
- **ภาพที่ ข.4:** ผลการทดสอบระบบรักษาความปลอดภัย SecDash HTTP Basic Authentication ตอบกลับ HTTP 401 Unauthorized พร้อม WWW-Authenticate  
- **ภาพที่ ข.5:** ผลการทดสอบระบบ Nginx Micro-Cache ตอบกลับส่วนหัว X-Cache-Status: HIT  
- **ภาพที่ ข.6:** ผลการตรวจสอบการตั้งค่า SSH Hardening (`sshd -T`) และกฎไฟร์วอลล์ iptables ควบคู่กับ ipset (`th_allow`)  
- **ภาพที่ ข.7:** ผลการตรวจสอบสถานะ Fail2ban ครบทั้ง 3 Jails (`sshd`, `wp-login`, `nginx-http-auth`) พร้อมตัวนับการตรวจจับ 119 เหตุการณ์  
- **ภาพที่ ข.8:** ผลการทดสอบการเชื่อมต่อจากเครือข่ายต่างประเทศ (Foreign GeoIP Timeout Test) ยืนยันการ Drop แพ็กเก็ตของ iptables
